# Multi-objective 5G NR scheduler: ns-3/5G-LENA code + stand-in simulator + analysis

## What is here and what has been run
| Part | Status |
|---|---|
| `sim/nrsim.cc` stand-in simulator + `run_experiments.py --backend sim` + `analyze.py` | **Built and run here**: smoke, quick (540 runs) and full (8,235 runs, 0 failures). Results in `results/sim/` |
| `ns3-nr/` (scheduler classes, scenario, `setup.sh`, `verify_api.sh`) | **Written, NOT compiled or run.** The `nr` module (gitlab.com) and nsnam.org were blocked in the authoring environment. API names marked `[VERIFY]` come from memory of the nr sources. Expect to fix a few symbols; `verify_api.sh` lists them. |

**Do not report the `results/sim` numbers as 5G-LENA results.** Run the ns-3 backend on your machine and re-run `analyze.py`.

## Quick start (stand-in, any Linux with g++, python3, pandas, matplotlib, pyyaml)
```
g++ -O2 -std=c++17 -o sim/nrsim sim/nrsim.cc
python3 run_experiments.py --backend sim --mode smoke     # 7 runs
python3 run_experiments.py --backend sim --mode quick     # 540 runs, ~20 s
python3 run_experiments.py --backend sim --mode full      # 8,235 runs, ~7 min on 2 cores, resumable
python3 analyze.py --backend sim --mode full              # tables + figures in results/sim/full/
```
## Real ns-3 + 5G-LENA (your machine, needs gitlab.com access)
```
cd ns3-nr && ./setup.sh                 # apt deps, clone nr + matching ns-3, verify API, patch, build, run stock example
python3 run_experiments.py --backend ns3 --ns3dir ~/ns-3-dev --mode smoke
python3 run_experiments.py --backend ns3 --ns3dir ~/ns-3-dev --mode quick
python3 analyze.py --backend ns3 --mode quick
```
If `verify_api.sh` prints MISSING, adapt `ns3-nr/nr-patch/*` and `ns3-nr/scratch/nr-multiobj-scenario.cc` to your nr release
(compare with `contrib/nr/examples/cttc-nr-demo.cc`), then `./apply_patch.sh ~/ns-3-dev && cd ~/ns-3-dev && ./ns3 build`.
Time per ns-3 run is unknown until you measure it; the full mode (~8,200 runs) is only practical if a run takes seconds. Use
`quick` first and scale `modes` in `scenarios.yaml`.
Run the validation: `--sched=MULTIOBJ --wC=1 --wF=0 --wD=0 --wQ=0` must match `--sched=MR` (true in the stand-in).

## Layout
`scenarios.yaml` (9 scenarios + modes) | `common.py` (simplex, J) | `run_experiments.py` | `analyze.py` | `RESULTS.md`
`sim/` stand-in | `ns3-nr/` real-stack code | `results/<backend>/raw` (per-run CSV, delay quantiles) | `results/<backend>/<mode>/{tables,figs,tuning_summary.csv,summary.json}`

## Design notes
* Objective: J = a*T + b*F + g*(1-D) + d*U. T and D are min-max normalised over all runs (candidates + baselines) with the same
  (scenario, seed); F is Jain's index (default: over demand-normalised throughput, `--fairness F_raw` for Eq. 10); U = allocated RBG fraction.
  w* = highest J averaged over scenarios and seeds. Sensitivity sets in `common.py:J_SETS`.
* Traffic per UE (UDP/CBR): eMBB 5QI 8 (20 Mbps, 1200 B, PDB 300 ms), URLLC 5QI 82 (200 B / 1 ms, PDB 10 ms), mMTC 5QI 9 (100 B / 10 ms, PDB 300 ms). Mixed = 50/25/25.
* Identical traffic/channel across schedulers: RNG streams depend only on (seed, UE). Check in `summary.json` (`identical_traffic_across_schedulers`).
* OFDMA only (TDMA twin class is generated by `apply_patch.sh` but untested).

## Model limitations (stand-in)
Single cell, no interference, wideband Rayleigh fading, 17 RBGs of 16 PRBs, CQI every 10 slots, logistic BLER (10% at the CQI
threshold), chase-combining HARQ (4 tx), RLC buffer 500 kB, 3GPP UMi/UMa path loss at 3.5 GHz, `QOS` is an approximation of nr's
QoS scheduler. See `sim/nrsim.cc` header.
